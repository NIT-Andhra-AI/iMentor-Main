## Module 1: Embedded Software Development & Lifecycle Models

### 1.1 Microprocessor vs. Microcontroller Architecture

Embedded systems are specialized computing platforms engineered to perform dedicated functions with real-time constraints, high reliability, and low power consumption. A fundamental architectural distinction lies between general-purpose **Microprocessors (MPUs)** and integrated **Microcontrollers (MCUs)**.

| Feature / Attribute | Microprocessor (MPU) | Microcontroller (MCU) |
| :--- | :--- | :--- |
| **Core Architecture** | Processing core only (CPU: ALU, Control Unit, Registers). | Integrated system-on-chip (CPU + Memory + Peripherals). |
| **Memory Configuration** | External RAM (DRAM/SDRAM) and ROM/Flash via system buses. | Internal SRAM (e.g., 32KB–512KB) and Flash (e.g., 128KB–2MB). |
| **System Peripherals** | External ICs connected via chipselects, PCI, or expansion buses. | On-chip GPIO, Timers, ADC/DAC, UART, SPI, I2C, CAN, USB. |
| **Memory Architecture** | Predominantly Von Neumann (shared bus for code and data). | Predominantly Harvard Architecture (separate instruction/data buses). |
| **Power Consumption** | High (Watts to tens of Watts). Requires active thermal management. | Very Low (milliWatts to microWatts). Suited for battery operation. |
| **Cost & Physical Size** | High system board complexity, multi-layer PCB, higher cost. | Low system cost, highly compact single-chip solution. |
| **Typical Applications** | PCs, Servers, Smartphones, High-end Multimedia Systems. | Automotive ECUs, Industrial Controllers, Medical Devices, IoT Nodes. |

```
Von Neumann Architecture:
+-------------------------------------------------------------+
|                          CPU Core                           |
+------------------------------+------------------------------+
                               | Shared Data & Instruction Bus
+------------------------------v------------------------------+
|                     Unified Memory Space                     |
|                   (Program Code + Data RAM)                 |
+-------------------------------------------------------------+

Harvard Architecture (Cortex-M4):
+-------------------------------------------------------------+
|                          CPU Core                           |
+------------------------------+------------------------------+
         I-Code Bus            |            D-Code Bus
+------------------------------+------------------------------+
|   Instruction Memory (Flash) |      Data Memory (SRAM)      |
+------------------------------+------------------------------+
```

#### Bus Structures & Memory Interfacing
Modern microcontrollers like the ARM Cortex-M4 utilize advanced multi-master bus fabrics (such as the AHB-Lite bus matrix). This allows concurrent execution: the instruction bus fetches code from Flash memory while the data bus simultaneously reads/writes to SRAM or peripheral registers without bus contention.

### 1.2 Embedded System Design Metrics

Designing an embedded system requires navigating complex, often conflicting engineering trade-offs. The key design metrics include:

1. **Non-Recurring Engineering (NRE) Cost:** The one-time cost of designing, engineering, prototyping, and testing the system.
2. **Unit Cost:** The monetary cost of manufacturing each individual product unit (BOM + fabrication + assembly).
   $$\text{Total Cost per Unit} = \frac{\text{NRE Cost}}{N} + \text{Unit Cost}$$
   where $N$ is the total production volume.
3. **Power Dissipation:** Static (leakage) and dynamic power consumption.
   $$P_{\text{dynamic}} = \alpha \cdot C_L \cdot V_{DD}^2 \cdot f_{\text{clk}}$$
   where $\alpha$ is the activity factor, $C_L$ is the capacitive load, $V_{DD}$ is operating voltage, and $f_{\text{clk}}$ is clock frequency.
4. **Performance Metrics:**
   - **Latency ($\tau$):** Time elapsed between an event trigger and the system's final response.
   - **Throughput ($TP$):** Quantity of data processed per unit time ($\text{samples/sec}$ or $\text{bits/sec}$).
5. **Physical Constraints:** Board size, component footprint, weight, thermal dissipation envelope.
6. **Time-to-Market (TTM):** The duration from concept inception to product commercialization. Delaying market release can reduce lifetime revenue drastically:
   $$\text{Revenue Loss \%} \approx \frac{D (3W - D)}{2 W^2} \times 100\%$$
   where $W$ is market lifetime and $D$ is time-to-market delay.

### 1.3 Software Lifecycle Models in Embedded Systems

#### 1.3.1 The Waterfall Model
The Waterfall model is a sequential, linear software engineering process comprising distinct phases:

```
[ Requirements Analysis ]
          │
          ▼
    [ System Design ]
          │
          ▼
   [ Implementation ]
          │
          ▼
    [ Verification ]
          │
          ▼
    [ Maintenance ]
```

* **Pros:** Simple, well-documented, clear milestones for fixed-requirement projects.
* **Cons in Embedded Systems:** Inability to accommodate hardware changes late in development. Hardware-software co-design requires concurrent iterations; Waterfall delays integration until late in the lifecycle, risking catastrophic hardware-software mismatch.

#### 1.3.2 The V-Model (Verification & Validation Model)
The V-Model explicitly pairs each development phase with a corresponding testing phase, ensuring rigorous validation:

```
    Development Phase                         Verification & Validation Phase
 Requirements Specifications ──────────────────────────► User Acceptance Testing
            │                                                      ▲
            ▼                                                      │
    System Architecture ─────────────────────────────────► System Integration Testing
            │                                                      ▲
            ▼                                                      │
     Module Design ──────────────────────────────────────► Sub-system Unit Testing
            │                                                      ▲
            ▼                                                      │
    Hardware/Software Implementation (Coding) ─────────────────────┘
```

* **Unit Testing:** Validates low-level drivers, math libraries, and peripheral routines.
* **Integration Testing:** Validates peripheral-to-core interfaces, stack sizes, and interrupt handling.
* **System Testing:** Validates end-to-end real-time response, timing constraints, and power modes.

### 1.4 Concurrency, Multi-Tasking & Scheduling

#### 1.4.1 Sequential vs. Concurrent Execution Models
* **Sequential Execution:** Programs execute instructions line-by-line within a single thread of control. Unsuited for real-time reactive systems.
* **Foreground/Background Architecture (Interrupt-Driven Loop):**
  - **Background (Main Loop):** Executes non-critical sequential tasks continuously.
  - **Foreground (ISRs):** Asynchronous hardware interrupts trigger high-priority event handlers.

```c
// Example Foreground/Background Architecture in C
volatile uint8_t flag_adc_complete = 0;
volatile uint16_t adc_value = 0;

void ADC1_IRQHandler(void) {
    if (ADC1->SR & ADC_SR_EOC) {
        adc_value = (uint16_t)ADC1->DR; // Read conversion result
        flag_adc_complete = 1;          // Set event flag
    }
}

int main(void) {
    Hardware_Init();
    while (1) {
        if (flag_adc_complete) {
            flag_adc_complete = 0;
            Process_ADC_Data(adc_value);
        }
        Perform_Background_Diagnostics();
    }
}
```

#### 1.4.2 Static vs. Dynamic Real-Time Scheduling

##### Rate Monotonic Scheduling (RMS)
RMS is a static, fixed-priority, preemptive scheduling algorithm for independent periodic tasks.
- **Priority Rule:** Tasks with shorter periods (higher frequencies) are assigned higher static priorities.
- **Schedulability Utilization Bound (Liu & Layland, 1973):**
  For $n$ periodic tasks, the total CPU utilization $U$ is:
  $$U = \sum_{i=1}^{n} \frac{C_i}{T_i} \le n \left(2^{1/n} - 1\right)$$
  where $C_i$ is worst-case execution time (WCET) and $T_i$ is task period.

As $n \to \infty$:
$$\lim_{n \to \infty} n \left(2^{1/n} - 1\right) = \ln(2) \approx 0.693$$

> **Theorem:** If $U \le n(2^{1/n} - 1)$, the task set is guaranteed to be schedulable under RMS. If $n(2^{1/n} - 1) < U \le 1.0$, the task set may be schedulable, requiring Exact Frame/Response Time Analysis (RTA):
> $$R_i^{k+1} = C_i + \sum_{j \in hp(i)} \left\lceil \frac{R_i^k}{T_j} \right\rceil C_j$$

##### Earliest Deadline First (EDF)
EDF is a dynamic priority scheduling algorithm where the task closest to its absolute deadline receives highest priority.
- **Schedulability Criterion:** A task set is schedulable under EDF if and only if:
  $$U = \sum_{i=1}^{n} \frac{C_i}{T_i} \le 1.0 \quad (100\% \text{ Processor Utilization})$$

### 1.5 Embedded Software Unit Testing

#### 1.5.1 Equivalence Partitioning & Boundary Value Analysis (BVA)
* **Equivalence Partitioning:** Inputs are split into valid and invalid contiguous sets. Tests sample representative values from each partition.
* **Boundary Value Analysis (BVA):** Errors frequently cluster at boundaries. Test cases evaluate $\{Minimum - 1, Minimum, Minimum + 1, Maximum - 1, Maximum, Maximum + 1\}$.

#### 1.5.2 Cyclomatic Complexity & Code Coverage
Cyclomatic complexity $V(G)$ quantifies the control flow complexity of a program graph $G$:
$$V(G) = E - N + 2P$$
where $E$ = number of edges, $N$ = number of nodes, $P$ = number of connected components (usually 1).
Alternatively, for decision nodes $D$:
$$V(G) = D + 1$$

* **Code Coverage Criteria:**
  - **Statement Coverage:** Percentage of executable statements tested.
  - **Branch/Decision Coverage:** Percentage of control flow branches (True/False) exercised.
  - **Modified Condition/Decision Coverage (MC/DC):** Requires that each condition in a decision independently affects the outcome. Crucial for safety-critical systems (ISO 26262, DO-178C).

#### 1.5.3 Hardware Register Mocking Test Bench in Embedded C
To test embedded software on host platforms (e.g., x86 host machine), hardware registers are mocked using pointer redirection or struct redefinition:

```c
// Mocking STM32 GPIO Register Map for Host Unit Testing
#include <stdio.h>
#include <stdint.h>
#include <assert.h>

typedef struct {
    volatile uint32_t MODER;   // Mode register
    volatile uint32_t OTYPER;  // Output type register
    volatile uint32_t OSPEEDR; // Output speed register
    volatile uint32_t PUPDR;   // Pull-up/pull-down register
    volatile uint32_t IDR;     // Input data register
    volatile uint32_t ODR;     // Output data register
    volatile uint32_t BSRR;    // Bit set/reset register
} GPIO_TypeDef;

// Instantiate mock peripheral in RAM
GPIO_TypeDef Mock_GPIOA;
#define MOCK_GPIOA (&Mock_GPIOA)

// Function under test
void LED_TurnOn(GPIO_TypeDef* GPIOx, uint8_t pin) {
    GPIOx->BSRR = (1U << pin); // Set bit
}

void LED_TurnOff(GPIO_TypeDef* GPIOx, uint8_t pin) {
    GPIOx->BSRR = (1U << (pin + 16)); // Reset bit
}

// Unit Test Suite
void test_LED_Control(void) {
    Mock_GPIOA.BSRR = 0x00000000;
    
    LED_TurnOn(MOCK_GPIOA, 5);
    assert(Mock_GPIOA.BSRR == (1U << 5));
    printf("[PASS] LED_TurnOn Test\n");

    LED_TurnOff(MOCK_GPIOA, 5);
    assert(Mock_GPIOA.BSRR == (1U << 21));
    printf("[PASS] LED_TurnOff Test\n");
}

int main(void) {
    test_LED_Control();
    return 0;
}
```

#### Detailed Breakdown of Program Status Register (xPSR)
The 32-bit `xPSR` is a composite of three logical status registers:

```
 Bit 31 30 29 28 27   26  25  24 23         16 15 10 9      8 7           0
+--+--+--+--+------+---+---+---+-------------+-----+--+------+-------------+
| N| Z| C| V|  Q   |  ICI/IT   |  Reserved   |ICI/IT|  T   | Interrupt   |
|  |  |  |  |      |   (25:26) |             |(15:10)| (24) | Vector (8:0)|
+--+--+--+--+------+---+---+---+-------------+-----+--+------+-------------+
|<----- APSR ----->|<------- EPSR ------------>|      |<--- IPSR ------>|
```

- **APSR (Application PSR):**
  - $N$ (Bit 31): Negative result flag.
  - $Z$ (Bit 30): Zero result flag.
  - $C$ (Bit 29): Carry/Borrow flag.
  - $V$ (Bit 28): Overflow flag.
  - $Q$ (Bit 27): Saturation flag (DSP instructions).
- **EPSR (Execution PSR):**
  - $T$ (Bit 24): Thumb bit. **Must always be 1** on Cortex-M4. A zero causes a `HardFault` (UsageFault - Invalid State).
  - $IT/ICI$ (Bits 26-25, 15-10): If-Then execution state bits / Interruptible-Continuable Instruction state.
- **IPSR (Interrupt PSR):**
  - Contains the exception number currently being executed (0 = Thread mode, 15 = SysTick, 16+ = External IRQ0+).

### 2.3 Cortex-M4 Memory Map & Bit-Banding Operations

The ARM Cortex-M4 features a unified 4 Gigabyte ($2^{32}$ bytes) flat address space.

```
Address Range                 Memory Region          Description / Usage
+---------------------------+----------------------+---------------------------------------+
| 0xFFFFFFFF - 0xE0100000   | Vendor Specific      | System peripherals & vendor devices   |
| 0xE0000000 - 0xE00FFFFF   | Private Peripheral   | NVIC, SysTick, MPU, Core Debug        |
| 0xA0000000 - 0xDFFFFFFF   | External Device      | External memory mapped peripherals    |
| 0x60000000 - 0x9FFFFFFF   | External RAM         | Off-chip SRAM / SDRAM / NOR Flash     |
| 0x40000000 - 0x5FFFFFFF   | Peripheral Region    | On-chip Peripherals (GPIO, Timers...) |
|   [0x40000000-0x400FFFFF] | (Bit-Band Region)    | 1 MB Bit-bandable Peripheral space    |
|   [0x42000000-0x43FFFFFF] | (Bit-Band Alias)     | 32 MB Alias space (1 bit -> 1 word)   |
| 0x20000000 - 0x3FFFFFFF   | SRAM Region          | On-chip SRAM                          |
|   [0x20000000-0x200FFFFF] | (Bit-Band Region)    | 1 MB Bit-bandable SRAM space          |
|   [0x22000000-0x23FFFFFF] | (Bit-Band Alias)     | 32 MB Alias space (1 bit -> 1 word)   |
| 0x00000000 - 0x1FFFFFFF   | Code Region          | Internal Flash, Boot ROM, Vector Table|
+---------------------------+----------------------+---------------------------------------+
```

#### Bit-Banding Derivation & Formulas
Bit-banding maps a 1 Megabyte bit-band target region into a 32 Megabyte bit-band alias region. Every single bit modification in the target region is converted into an atomic single 32-bit word write/read in the alias region.

**Derivation of Bit-Band Alias Address Equation:**
1. A 1 MB target region contains $1,048,576 \text{ bytes} \times 8 \text{ bits/byte} = 8,388,608 \text{ bits}$.
2. Each bit maps to a distinct 32-bit (4-byte) word in the alias region.
3. Total Alias Memory Required = $8,388,608 \text{ words} \times 4 \text{ bytes/word} = 33,554,432 \text{ bytes} = 32 \text{ MB}$.

##### Formula:
$$\text{Alias Address} = \text{Alias Base} + (\text{Byte Offset} \times 32) + (\text{Bit Number} \times 4)$$

Where:
- For SRAM: $\text{Alias Base} = \mathtt{0x22000000}$, Target Base = $\mathtt{0x20000000}$.
- For Peripherals: $\text{Alias Base} = \mathtt{0x42000000}$, Target Base = $\mathtt{0x40000000}$.
- $\text{Byte Offset} = \text{Target Address} - \text{Target Region Base}$.
- $\text{Bit Number} \in [0, 7]$.

---

#### Solved Bit-Banding Examples

##### Worked Example 1: SRAM Bit-Banding
**Problem:** Calculate the bit-band alias address corresponding to bit 3 of SRAM memory location `0x2000C024`.

**Solution:**
1. Determine Target Region Base for SRAM: $\text{SRAM\_BASE} = \mathtt{0x20000000}$.
2. Calculate Byte Offset:
   $$\text{Byte Offset} = \mathtt{0x2000C024} - \mathtt{0x20000000} = \mathtt{0xC024} = 49,188 \text{ bytes (decimal)}$$
3. Identify Target Bit: $\text{Bit Number} = 3$.
4. Apply the formula:
   $$\text{Alias Addr} = \mathtt{0x22000000} + (\mathtt{0xC024} \times 32) + (3 \times 4)$$
   $$\mathtt{0xC024} \times 32 = \mathtt{0xC024} \times \mathtt{0x20} = \mathtt{0x180480}$$
   $$3 \times 4 = 12 = \mathtt{0x0C}$$
   $$\text{Alias Addr} = \mathtt{0x22000000} + \mathtt{0x180480} + \mathtt{0x0C} = \mathtt{0x2218048C}$$

**Result:** The alias memory address is `0x2218048C`. Writing `0x01` to `*(((volatile uint32_t*)0x2218048C))` sets bit 3 of `0x2000C024` atomically.

---

##### Worked Example 2: Peripheral Bit-Banding
**Problem:** Find the alias address to toggle Bit 5 of GPIOA output data register (`GPIOA_ODR`), located at address `0x40020014`.

**Solution:**
1. Peripheral Target Base: $\text{PERIPH\_BASE} = \mathtt{0x40000000}$.
2. Byte Offset:
   $$\text{Byte Offset} = \mathtt{0x40020014} - \mathtt{0x40000000} = \mathtt{0x20014}$$
3. Bit Number: 5.
4. Calculation:
   $$\text{Alias Addr} = \mathtt{0x42000000} + (\mathtt{0x20014} \times 32) + (5 \times 4)$$
   $$\mathtt{0x20014} \times 32 = \mathtt{0x20014} \times \mathtt{0x20} = \mathtt{0x400280}$$
   $$5 \times 4 = 20 = \mathtt{0x14}$$
   $$\text{Alias Addr} = \mathtt{0x42000000} + \mathtt{0x400280} + \mathtt{0x14} = \mathtt{0x42400294}$$

### 2.4 ARM & Thumb-2 Instruction Set Architecture

The Cortex-M4 executes the **Thumb-2** instruction set, which seamlessly blends 16-bit and 32-bit instructions to achieve high code density while retaining 32-bit RISC processing performance.

#### Data Processing & Arithmetic Instructions
```assembly
; ARM Assembly Examples
MOV   R0, #0x45          ; Load immediate value 0x45 into R0
ADD   R2, R1, R0         ; R2 = R1 + R0
SUB   R3, R1, #10        ; R3 = R1 - 10
MUL   R4, R2, R3         ; R4 = R2 * R3 (32-bit multiplication)
MLA   R5, R1, R2, R3     ; R5 = (R1 * R2) + R3 (Multiply-Accumulate)
UDIV  R6, R2, R1         ; Unsigned Division: R6 = R2 / R1
SDIV  R7, R2, R1         ; Signed Division: R7 = R2 / R1
CMP   R0, #50            ; Compare R0 with 50 (Updates N, Z, C, V in APSR)
TST   R1, #0x01          ; Test bit 0 of R1 (APSR Z flag set if bit is 0)
```

#### Bitfield Operations
```assembly
BFC   R0, #4, #8         ; Bit Field Clear: Clears 8 bits in R0 starting at bit 4
BFI   R0, R1, #8, #4     ; Bit Field Insert: Inserts lower 4 bits of R1 into R0 at bit 8
UBFX  R2, R0, #12, #4    ; Unsigned Bit Field Extract: Extracts 4 bits from R0 at bit 12 -> R2
CLZ   R3, R0             ; Count Leading Zeros: Returns number of zero bits before first '1'
RBIT  R4, R0             ; Reverse Bits: Reverses all 32 bits in R0
```

#### Branch & Control Flow Instructions
```assembly
B     label              ; Unconditional branch to label
BL    subroutine         ; Branch with Link: Store return PC in LR (R14), jump to subroutine
BX    LR                 ; Branch and Exchange: Return from subroutine using LR
CBZ   R0, zero_label     ; Compare and Branch if Zero (16-bit Thumb instruction)
CBNZ  R1, nonzero_label  ; Compare and Branch if Non-Zero
```

##### If-Then (IT) Conditional Blocks
The `IT` block enables conditional execution of up to 4 subsequent instructions without incurring branch penalty overhead.

**Syntax Structure:** `IT[T/E][T/E][T/E] <condition>`
- `T` = Then (Executes when condition is true).
- `E` = Else (Executes when condition is false).

```assembly
; Assembly Example: IT Block
CMP   R0, R1             ; Compare R0 and R1
ITEET GT                 ; If Greater Than (GT): Then, Else, Else, Then
ADDGT R2, R0, R1         ; (T) Executed if R0 > R1: R2 = R0 + R1
SUBLE R3, R0, R1         ; (E) Executed if R0 <= R1: R3 = R0 - R1
MOVLE R4, #0             ; (E) Executed if R0 <= R1: R4 = 0
MULGT R5, R2, R0         ; (T) Executed if R0 > R1: R5 = R2 * R0
```

#### 2.4.1 Single-Precision Floating-Point Unit (FPU / FPv4-SP)
The Cortex-M4 FPU hardware accelerates 32-bit single-precision IEEE 754 floating-point operations.

- **FPU Register File:** 32 single-precision registers (`S0` to `S31`), accessible as 16 double-word registers (`D0` to `D15`).
- **FPSCR (Floating-Point Status and Control Register):** Stores arithmetic flags ($N, Z, C, V$) and controls rounding modes and divide-by-zero traps.

```assembly
; Assembly FPU Instructions
VLDM   R0!, {S0-S2}      ; Vector Load Multiple: Load 3 float values from [R0] into S0, S1, S2
VADD.F32 S3, S0, S1      ; Single-precision addition: S3 = S0 + S1
VMUL.F32 S4, S3, S2      ; Single-precision multiplication: S4 = S3 * S2
VSQRT.F32 S5, S4         ; Square root calculation: S5 = sqrt(S4)
VCVT.F32.S32 S6, S7      ; Convert Signed 32-bit Integer (S7) to 32-bit Float (S6)
```

```c
// C Example utilizing Hardware FPU
#include <arm_math.h>

float32_t Calculate_RMS_Filter(float32_t sample1, float32_t sample2) {
    float32_t sum_squares;
    // Core delegates math directly to hardware FPU instructions (VADD.F32, VMUL.F32, VSQRT.F32)
    sum_squares = (sample1 * sample1) + (sample2 * sample2);
    return sqrtf(sum_squares / 2.0f);
}
```

## Module 3: Interrupts, Peripherals & Interfacing

### 3.1 Exception & Interrupt Handling Architecture (NVIC)

The Nested Vectored Interrupt Controller (NVIC) manages all core exceptions and external peripheral interrupts on the Cortex-M4.

```
Vector Table Layout (Base Address 0x00000000 or relocated via VTOR):
Offset       Vector Entry                Type
+----------+---------------------------+-----------------------------------+
| 0x000000 | Initial Stack Pointer     | MSP Value (Top of SRAM)           |
| 0x000004 | Reset Handler             | Program Entry Point               |
| 0x000008 | Non-Maskable Interrupt    | NMI Handler                       |
| 0x00000C | HardFault Handler         | Hardware Error Exception          |
| 0x000010 | MemManage Fault           | Memory Protection Exception       |
| 0x000014 | BusFault                  | Bus Error / Invalid Access        |
| 0x000018 | UsageFault                | Undefined Instruction / Div zero  |
| ...      | Reserved                  | Reserved entries                  |
| 0x00002C | SVCall Handler            | Supervisor Call (System Call)     |
| 0x000038 | PendSV Handler            | Pended Interrupt for Context SW  |
| 0x00003C | SysTick Handler           | System Tick Timer Exception       |
| 0x000040 | External IRQ0             | Peripheral Interrupt 0 (e.g. WWDG)|
| 0x000044 | External IRQ1             | Peripheral Interrupt 1 (e.g. EXTI)|
+----------+---------------------------+-----------------------------------+
```

#### Preemption Priority & Sub-Priority Grouping
The NVIC supports up to 256 priority levels split via the `AIRCR` register's `PRIGROUP` field into:
1. **Preemption Priority:** Determines if an incoming interrupt can preempt (nest inside) an currently executing ISR.
2. **Sub-priority:** Determines execution precedence if multiple interrupts with identical preemption priority trigger simultaneously.

```
       8-Bit Priority Register Structure (STM32 implements upper 4 bits):
       Bit 7   Bit 6   Bit 5   Bit 4   Bit 3   Bit 2   Bit 1   Bit 0
      +-------+-------+-------+-------+-------+-------+-------+-------+
      | Preemption Priority   | Sub-Priority  |      Unimplemented    |
      +-------+-------+-------+-------+-------+-------+-------+-------+
```

#### Stacking, Tail-Chaining, & Latency Derivation

##### Interrupt Entry Hardware Stacking Process:
Upon exception entry, the core automatically pushes an 8-word stack frame (32 bytes) onto the active stack pointer (MSP or PSP):

```
       Higher Memory Addresses
      +-----------------------+
      |        xPSR           |  <-- Stack Pointer + 28
      |      Return PC        |  <-- Stack Pointer + 24
      |       LR (R14)        |  <-- Stack Pointer + 20
      |         R12           |  <-- Stack Pointer + 16
      |         R3            |  <-- Stack Pointer + 12
      |         R2            |  <-- Stack Pointer + 8
      |         R1            |  <-- Stack Pointer + 4
      |         R0            |  <-- Stack Pointer (MSP/PSP)
      +-----------------------+
       Lower Memory Addresses
```

##### Tail-Chaining Mechanics:
When an ISR finishes and another interrupt of equal or lower preemption priority is pending, the core skips the unstacking and re-stacking steps. Instead, it performs **Tail-Chaining**:
- **Standard Unstacking + Stacking Latency:** $12 + 12 = 24 \text{ clock cycles}$.
- **Tail-Chaining Latency:** **6 clock cycles**.
- **Performance Savings:** Saves 18 clock cycles per chained interrupt.

```
Standard Interrupt Flow:
[ Executing Main ] ──► [ Stacking: 12 cycles ] ──► [ ISR 1 ] ──► [ Unstacking: 12 cycles ] ──► [ Stacking: 12 cycles ] ──► [ ISR 2 ]
                                                                 └────────── 24 cycles total ──────────┘

Tail-Chaining Optimization:
[ Executing Main ] ──► [ Stacking: 12 cycles ] ──► [ ISR 1 ] ──► [ Tail-Chain: 6 cycles ] ──► [ ISR 2 ] ──► [ Unstacking: 12 cycles ]
                                                                 └── Saves 18 cycles ──┘
```

##### Interrupt Latency Equation:
$$\text{Latency}_{\text{zero-wait-state}} = 12 \text{ clock cycles}$$
If a memory access involves $N$ wait states, Latency increases:
$$\text{Latency} = 12 + (\text{Wait States} \times \text{Access Count})$$

#### 3.3.1 Successive Approximation Register (SAR) ADC Architecture

```

                          ▼                               │
```

##### SAR ADC Operation Steps:
1. **Sample & Hold:** Sample switch closes to charge internal sampling capacitor $C_{\text{sample}}$ for duration $t_{\text{sample}}$.
2. **Binary Search Iteration:** For an $N$-bit ADC, the SAR controller executes $N$ clock cycles, comparing $V_{\text{in}}$ against internal DAC levels starting at Most Significant Bit (MSB, $\frac{V_{\text{ref}}}{2}$).

##### Total ADC Conversion Time Equation:
$$t_{\text{conv}} = t_{\text{sample}} + t_{\text{SAR}} = t_{\text{sample}} + (N \times T_{\text{ADC\_CLK}})$$

---

##### Solved ADC Conversion Numerical
**Problem:** An 12-bit SAR ADC operates with an ADC clock frequency $f_{\text{ADC}} = 16 \text{ MHz}$. The sample time is configured to $84 \text{ ADC clock cycles}$. Calculate:
1. Total time required for a single ADC conversion ($t_{\text{conv}}$).
2. Maximum sampling rate in samples per second ($\text{SPS}$).

**Solution:**
1. Determine ADC clock period:
   $$T_{\text{ADC\_CLK}} = \frac{1}{f_{\text{ADC}}} = \frac{1}{16 \times 10^6 \text{ Hz}} = 62.5 \text{ ns}$$
2. Calculate total conversion cycles for 12-bit resolution ($N = 12$):
   $$\text{Total Cycles} = \text{Sample Cycles} + N = 84 + 12 = 96 \text{ clock cycles}$$
3. Compute total conversion time $t_{\text{conv}}$:
   $$t_{\text{conv}} = 96 \times 62.5 \text{ ns} = 6,000 \text{ ns} = 6.0 \ \mu\text{s}$$
4. Calculate Maximum Sampling Rate:
   $$\text{Sampling Rate} = \frac{1}{t_{\text{conv}}} = \frac{1}{6.0 \times 10^{-6} \text{ s}} \approx 166,667 \text{ Samples/sec} = 166.67 \text{ kSPS}$$

##### Baud Rate Fractional Divider Equation:
$$\text{Baud Rate} = \frac{f_{\text{CK}}}{16 \times \text{USARTDIV}}$$
$$\text{USARTDIV} = \frac{f_{\text{CK}}}{16 \times \text{Baud Rate}}$$

##### Solved UART Baud Rate Numerical
**Problem:** Calculate the `USARTDIV` register value for an STM32 USART operating at $f_{\text{CK}} = 42 \text{ MHz}$ to achieve a standard baud rate of $115,200 \text{ bps}$. Break down the result into integer part (`DIV_Mantissa`) and fractional part (`DIV_Fraction`).

**Solution:**
1. Compute `USARTDIV`:
   $$\text{USARTDIV} = \frac{42 \times 10^6}{16 \times 115,200} = \frac{42,000,000}{1,843,200} \approx 22.786458$$
2. Extract Mantissa:
   $$\text{DIV\_Mantissa} = \lfloor 22.786458 \rfloor = 22 = \mathtt{0x16}$$
3. Compute 4-bit Fractional part ($16 \times \text{Fractional Remainder}$):
   $$\text{DIV\_Fraction} = \text{round}(0.786458 \times 16) = \text{round}(12.583) = 13 = \mathtt{0x0D}$$
4. Final 16-bit register value (`USART_BRR`):
   $$\text{USART\_BRR} = (\text{DIV\_Mantissa} \ll 4) \vert \text{DIV\_Fraction} = (22 \ll 4) \vert 13 = 352 \vert 13 = 365 = \mathtt{0x016D}$$

#### Context Switch Assembly Primitive (PendSV Handler)
During a context switch, the core pushes remaining registers (`R4`-`R11`) to the stack and updates the Task Control Block (TCB).

```assembly
; FreeRTOS Cortex-M4 PendSV Handler Context Switch Implementation
.global PendSV_Handler
.type PendSV_Handler, %function
PendSV_Handler:
    MRS     R0, PSP             ; Read Process Stack Pointer into R0
    CBZ     R0, First_Task_Start; Jump if first task starting
    
    ; Save remaining Callee-Saved Registers R4-R11
    STMDB   R0!, {R4-R11}       ; Push R4-R11 onto Task Stack
    
    LDR     R1, =pxCurrentTCB   ; Load current TCB address pointer
    LDR     R1, [R1]
    STR     R0, [R1]            ; Save updated SP to Current TCB top of stack

First_Task_Start:
    BL      vTaskSwitchContext  ; Call C scheduler function to update pxCurrentTCB
    
    LDR     R1, =pxCurrentTCB
    LDR     R1, [R1]
    LDR     R0, [R1]            ; R0 = new Task's SP
    
    LDMIA   R0!, {R4-R11}       ; Pop R4-R11 from new Task's Stack
    MSR     PSP, R0             ; Update PSP register
    
    ORR     LR, LR, #0x04       ; Ensure EXCRET uses PSP on return
    BX      LR                  ; Hardware automatically pops R0-R3, R12, LR, PC, xPSR
```

### 4.3 Mutexes, Semaphores, & Priority Inversion

#### Priority Inversion Problem & Priority Inheritance Solution

```
Priority Inversion Scenario:
 High Priority (H)  ─────► [ Blocked on Mutex ] ──────────────────────────► [ Acquires Mutex & Runs ]
 Medium Priority (M)─────►                [ Preempts L & Runs ] ──────►
 Low Priority (L)   ─────► [ Locks Mutex ] ──────────────────► [ Releases ]

Priority Inheritance Protocol (Solution):
 High Priority (H)  ─────► [ Blocked on Mutex ] ──────────────────────────► [ Acquires Mutex & Runs ]
 Low Priority (L)   ─────► [ Locks Mutex ] ──► [ Inherits Priority H ] ──► [ Releases & Drops Priority ]
```

```c
// Complete FreeRTOS C Code Example: Mutexes & Binary Semaphores
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xMutexUART;
SemaphoreHandle_t xBinarySemADC;

void Task_SensorRead(void *pvParameters) {
    for (;;) {
        // Wait for ADC Interrupt notification via Binary Semaphore
        if (xSemaphoreTake(xBinarySemADC, portMAX_DELAY) == pdTRUE) {
            // Lock UART Resource via Mutex (Protected against Priority Inversion)
            if (xSemaphoreTake(xMutexUART, pdMS_TO_TICKS(100)) == pdTRUE) {
                // Safely transmit reading over shared UART
                xSemaphoreGive(xMutexUART);
            }
        }
    }
}

void ADC_IRQHandler(void) {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    xSemaphoreGiveFromISR(xBinarySemADC, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}
```
